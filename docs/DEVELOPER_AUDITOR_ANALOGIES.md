# Developer workflows as analogies for an auditor work tool

**Research cut-off:** October 22, 2026  
**Purpose:** translate the open product questions into familiar developer workflows, then record what Codex currently documents for those workflows and where an auditor-focused product would need further study. This is a research aid, not a requirements list or design decision.

The analogies below are useful because Codex is built around making developers more effective in the environments and practices they already use. They do not imply that audit work is software development, or that developer controls map directly to audit controls. The full Codex capability inventory remains broader than these questions; this mapping does not narrow the study to coding, execution, analysis, agents, memory, or context.

**User clarification, October 26:** the intended product is essentially a Codex fork preserving its underlying experience and broad capabilities, redesigned for auditors. The central analogy is shared saved artifacts: the auditor can inspect work in the product or continue working in Excel, Word, PowerPoint, or another suitable editor, with assistance continuing around the same body of work. An API connection to each editor is not a prerequisite for this file-based path. Live application state and remote platform records are additional capabilities to study. This settles the direction recorded in Q5/Q13/Q15 of [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md); detailed design, reusable component boundaries, and delivery sequence remain open.

| **1. How is the work tailored to the practitioner or team?** Procedures, terminology, criteria, risk and sampling approaches, review roles, templates, reuse, and versioning. | A team configures its engineering conventions: supported languages and frameworks, repository rules, test/review standards, security requirements, deployment process, and definition of done. The rules differ by repository and team. | Codex has several customization layers: `AGENTS.md` instructions by scope, reusable skills, custom subagents, MCP connections, hooks, and configuration/managed policy. Instructions can be project-scoped; skills package repeatable workflows and references; subagents specialize tasks. These are mechanisms for shaping agent behavior, not a built-in audit methodology or approval framework. Study how configurations are versioned, inherited, selected, and reconciled when they conflict. Codex offers configuration mechanisms; it does not define the required audit-specific vocabulary, procedure model, or methodology lifecycle. |
| **2. What context should each piece of work use, and what should persist?** | A developer task draws on a code repository, issue/PR, design and API docs, logs, prior decisions, and a branch or worktree. The developer decides what belongs in the task and what stays in the codebase. | Codex can use a project/workspace, repository files and instructions, thread history, local memories where enabled, skills, and connected sources. Thread resumption and compaction support continuity; goals can carry a defined objective across a longer task. These mechanisms have different scopes: a thread is task history, instructions guide behavior, and memory is reusable context. None should be mistaken for a complete evidence file or an immutable audit record. [Projects and chats](https://learn.chatgpt.com/docs/projects), [Memories](https://learn.chatgpt.com/docs/customization/memories), [Long-running work](https://learn.chatgpt.com/docs/long-running-work) | Study context boundaries between engagements and tasks, source/version provenance, carry-forward rules, permitted reuse, and how an auditor can tell which material informed a result. Codex has general project and thread context; audit work may need stronger explicit source scoping and evidence lineage. |
| **3. Which sources and integrations are available, and under whose identity?** | A developer reads source control, issue tracking, CI, design docs, package registries, databases, and local files, using credentials scoped to the relevant service and repository. | Codex can work with local files and command-line tools, browser capabilities, MCP servers, plugins/connectors, and supported source-control workflows. External systems use their own authentication and access controls; local/cloud execution and host credentials affect available resources. The same task may therefore have different access depending on its execution location and connector identity. [MCP and external context](https://learn.chatgpt.com/docs/learn/best-practices), [Plugins and permissions](https://learn.chatgpt.com/docs/plugins), [Environments](https://learn.chatgpt.com/docs/environments/modes) | Study audit-system integrations and data access in terms of principal, source account, entity/scope, read/write authority, and evidence provenance. Determine how read-only and side-effecting operations are distinguished and explained. Codex supplies general integration and permission patterns, not audit-specific source authorization or evidence-access semantics. |
| **4. What outputs and records should the product own, and how do they move between systems?** | A developer's work product may be a patch, commit, pull request, review comment, test report, release artifact, or documentation update. The source repository, issue tracker, CI system, and release process remain the destinations of record. | Codex can create or edit workspace files, expose Git diffs for review, support commit/PR workflows through available clients and integrations, and be controlled through CLI/SDK/app-server interfaces. Users can inspect changes and decide what to stage, revert, commit, or share. Generated files are outputs; Codex does not make the destination system authoritative by itself. [Code review](https://learn.chatgpt.com/docs/code-review), [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk), [CLI reference](https://learn.chatgpt.com/docs/cli/reference) | Explore both operating modes: handoff to the practitioner's external system of record, or native engagement records in a built-in Diligent-like mode. Study what source references, scope, criteria/version, procedures, calculations, limitations, review status, and change history travel with an output or persist as a native record. |
| **5. How can analysis be checked and repeated?** | Developers reproduce a bug, run unit/integration tests, linters and builds, inspect logs and diffs, and ask a reviewer to check the change. Confidence depends on the test's coverage and the quality of the environment and inputs. | Codex can run commands and available scripts in its execution environment, inspect results, edit tests, and review Git changes. Its review surfaces report prioritized findings without changing the working tree; users still verify findings against behavior and tests. What can be run depends on the installed/configured environment. Codex does not guarantee correctness merely because a command completed or a reviewer agent found no issue. [Code review](https://learn.chatgpt.com/docs/code-review), [CLI](https://learn.chatgpt.com/docs/cli), [Execution environments](https://learn.chatgpt.com/docs/environments/modes) | Study repeatable analysis records: original inputs, query/code and parameters, transformation steps, population and sample definition, criteria versions, exceptions, recalculation/reperformance, and known limitations. Codex provides general-purpose execution and review; it does not impose audit sampling, evidence-sufficiency, or conclusion standards. |
| **6. How does a human steer work and review consequential results?** | A developer steers an agent, reviews diffs and test results, and decides whether to merge or release. The agent may be allowed to make routine in-scope edits while higher-impact operations require review. | Codex supports follow-up steering, planning and long-running goals, visible task activity, change review, and configured sandbox/approval controls. Eligible actions that already require approval can be routed to an automatic reviewer, but the reviewer does not expand permissions. A code review is feedback on a change, not an approval to merge; a user chooses whether to act on findings. [Long-running work](https://learn.chatgpt.com/docs/long-running-work), [Approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security), [Code review](https://learn.chatgpt.com/docs/code-review) | Study configurable human checkpoints and roles for the relevant practice: who prepares, supervises, reviews, approves, resolves disagreement, and releases an output. Separate approval to use a tool from professional review of evidence and conclusions. Codex's permission prompts and code-review workflow are useful analogies, not audit sign-off controls. |
| **7. Which Codex capabilities and surfaces fit, and what controls belong around them?** | Developers choose among IDE, terminal, desktop, CI/cloud, browser, and integrations depending on whether they are editing code, researching, testing, reviewing, or automating. A team applies safeguards appropriate to the capability and execution environment. | Codex spans more than code editing: CLI and desktop, IDE, local/worktree/cloud execution, mobile/remote control, files, browser and Computer Use, images, voice, MCP/plugins, skills/hooks, subagents, scheduling, sharing, publishing, security review, and administration/policy surfaces. For each candidate, consider practitioner value, data/action authority, reviewability, availability, and how work either transfers into the practitioner's external record system or persists in a built-in audit record mode. ## Reading the comparison

The eight questions above are now supplemented by the complete [Codex-to-auditor feature map](CODEX_AUDITOR_FEATURE_MAP.md) and [detailed behavioral mirror](CODEX_AUDITOR_FEATURE_MIRROR.md). Those documents retain every existing capability group and separately identify the audit enhancements needed to preserve its function and experience. The user's sequence is to finish that mirror before planning a V2 layer of additional functionality.

The strongest developer analogy is **adaptability around an existing body of work and its existing destination systems**. Codex already offers rich mechanisms for project guidance, reusable workflows, tools, execution, collaboration, review, and controls. The research question is how those mechanisms work across the entire product, then which concepts can be adapted for a flexible auditor work tool. Audit-specific procedures, evidence lineage, professional review, and handoff semantics are areas to investigate—not assumed requirements to impose on every practitioner.
