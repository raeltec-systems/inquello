# Codex-to-auditor feature map

**Date:** October 26, 2026. **Purpose:** map Codex as it is to an auditor experience, including the enhancements needed for that equivalent. This is the first functional mirror layer; V2 additions and architecture planning come afterwards.

The map covers **76 Codex capability groups and 3 separate composition lenses**, with **270 detailed subfeature mappings**, **93 proposed enhancements**, and **20 expanded behavior entries**. All baseline entries have a counterpart; none was removed because it seemed developer-specific or peripheral.

Microsoft Azure Foundry / Azure OpenAI is included as C54A alongside Amazon Bedrock, added at the user's request and sourced separately from the preserved original inventory.

**Subsequent research:** [pass 2](RESEARCH_PASS_02.md) records the accepted team/workspace/writeback defaults, Codex methodology mechanisms and pinned source traces. It also logs newly discovered GCP/Vertex provider support for a follow-up map entry; the counts here remain the reconciled inventory, not a claim that later discoveries are already included.

The audit column is our proposed product behavior. The [full mirror](CODEX_AUDITOR_FEATURE_MIRROR.md) contains the current developer behavior, trigger, inputs, actions, outputs, human control, subfeatures, evidence status and limitations for each row. [Nine worked examples](CODEX_AUDITOR_WORKED_EXAMPLES.md) demonstrate orientation, artifact production, change review, investigation, delegation, alternative analyses, advisory work, method reuse and handoff.

Preserve the Codex foundation and broad experience. Let auditors review supported artifacts internally or continue in existing tools using the same saved work. V1 uses external record systems; V2 adds built-in audit-record mode. Domain-specific readers, calculations, event adapters and review surfaces needed for the Codex-to-auditor equivalents remain first-layer adaptations; they are not automatically V2 features.

## Layer 1 adaptations and the later V2 layer

Layer 1 preserves a Codex capability's role and working loop while adapting its inputs, vocabulary, tools and reviewable outputs to auditors. Examples include workbook-aware change review, procedure-specific skills, evidence links, specialist review and triggered control testing. Required changes for those equivalents are listed in every feature card; technical effort does not decide whether a capability belongs in the mirror.

The user has assigned built-in audit-record mode to V2. V1 is the full Codex-derived workbench using external audit records and supported working files. Native authoritative record identities, relationships, sign-off history, controlled amendments, retention and export accompany the V2 mode; V1 retains work history, evidence references, review assistance and external delivery. Broad audit-universe/function management and a general workflow builder remain other, unprioritised V2 candidates. The [product brief](PRODUCT_BRIEF_V0_1.md) records this phase boundary; detailed sequencing within each phase remains open.

The next planning exercise should decide how to realise the mapped experience, using this inventory and the remaining evidence gaps. It should not repeat the already settled choice of whether the product should broadly mirror Codex.
