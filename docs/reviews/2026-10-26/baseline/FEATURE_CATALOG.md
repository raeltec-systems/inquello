# ChatGPT Work feature catalog for an auditor-tool study

**Research cut-off:** October 22, 2026  
**Method:** public OpenAI documentation and public source repository review. This is not a live, signed-in walkthrough of the Work client. Availability varies by plan, workspace policy, platform, region, and rollout. The catalog describes documented behavior, not hidden implementation.

**Coverage note:** This is an inventory of the Work feature families that public materials document, not a guarantee that every setting, integration, or recently rolled-out capability is available to every account. Public docs and feature availability change over time; confirm a specific surface against the account and workspace eventually studied.

## Product boundary

ChatGPT Work is the task-oriented work surface in ChatGPT. OpenAI describes it as a way to delegate substantial work that uses sources and tools and ends in a result the user can review. Codex is a distinct, developer-oriented agent product with a public open-source harness, CLI, app-server, SDK, and multiple clients. OpenAI's Enterprise/Edu Work Overview says Work and Codex share some core execution, isolation, and permission mechanisms; this is a bounded claim from those documented environments, not a claim about every account. The public `openai/codex` repository is a primary source for Codex's published harness and integration surfaces; it is **not ChatGPT Work's source code** and does not establish Work's internal design.

## User-facing feature inventory

The table includes Work-native behaviors and shared ChatGPT capabilities that may be available from Work when enabled. It does not imply that each capability is Work-exclusive or available on every plan, account, or surface. Codex-only controls are labeled separately.

| Feature | How it works, as documented | Auditor-tool relevance (interpretation) |
| --- | --- | --- |
| **Chat and Work modes** | On web/mobile, the user selects Work; on desktop, ChatGPT is selected and then Chat or Work. Chat is for answers and short drafts; Work is for multi-step tasks with a defined outcome. Work and Chat entries can appear together in Recents. Codex remains a separate view/history. | This is a mode switch between answering and doing. Auditor tasks map better to an engagement task than an unstructured Q&A, but the audit case lifecycle is not a documented Work feature. |
| **Outcome-oriented task request** | A prompt can name the outcome, source material/apps, constraints, quality criteria, and when the agent should stop for review. OpenAI recommends tasks that use multiple sources or steps and produce an output the user will review or reuse. | A task request can correspond to an audit objective or a bounded piece of fieldwork. It should not silently expand an approved engagement scope. |
| **Progress and long-running work** | Users can follow progress, answer questions, change direction, request a recap, and review the result. Work prompts can state an outcome, constraints, and completion/review criteria; continuing in the same chat carries the task context. The documented `/goal` controls to pause, resume, edit, or clear a persistent goal are in Codex desktop/CLI/IDE, not Work web. The docs do not specify a complete Work task state machine or checkpoint guarantee. | Useful for keeping an auditor in control during evidence requests, analysis, and drafting. A progress update or completed task alone is not evidence that a control test or engagement is complete. |
| **Reviewable outputs** | Work can return an analysis, brief, workflow, recurring update, or generated file such as a document, spreadsheet, or presentation. The user can request revisions and review the artifact in context. | Natural audit deliverables include draft test workpapers, evidence summaries, issue logs, and report drafts. The docs do not describe audit workpaper formats or certify generated material. |
| **Research and data analysis** | Deep Research, where available, investigates a question across multiple sources and returns a report with sources for review. Data analysis can inspect structured uploaded files and create tables or charts; a Data plugin can analyze connected business data. Method, calculations, code, assumptions, and source coverage still need user review. Search results and page content are untrusted input. | Possible uses include criteria research, population profiling, and exception summaries. The auditor must validate the population, calculations, methods, source coverage, and conclusion before relying on the result. |
| **Visualizations and Sites** | When enabled, a visualization tool can create interactive charts, diagrams, maps, calculators, simulations, or explanations. Sites can turn a description or source material into a site/dashboard that users preview, refine, save, deploy, and manage. Sites is a separately managed published output, distinct from a Work project; availability and publishing controls vary. A generated visualization is not necessarily a live, source-connected dashboard; rendering and export behavior vary. | Useful for exploration or communicating audit results. The chart or site should retain source, refresh date, calculation, and access context; a polished presentation is not evidence that underlying data is correct. |
| **Projects and related context** | Projects group related chats, files, and instructions. A user can begin Work from a project and use that project's context. Projects are suited to ongoing work whose source materials and instructions should remain together. | A project can resemble a container for an audit engagement. It is not equivalent to an audit record repository, controlled workpaper index, or engagement sign-off system. |
| **File and folder use** | Work can use attached or project files. In the desktop app, it can use local files when the user grants access and the tool is available. Web/mobile Work cannot directly read files on the user's computer. Local access is permissioned and does not mean the conversation/task context remains only on-device. | Engagement files would need source attribution, collection metadata, access restrictions, retention rules, and a way to tell source documents from generated files. Public Work docs do not establish those as audit-grade controls. |
| **File previews and annotations** | On desktop, supported generated documents, presentations, spreadsheets, PDFs, and HTML can open in a side-by-side preview; HTML can have rendered and source views. Users can select a supported preview region and ask for a targeted revision. On web, users review and download outputs in chat and give follow-up feedback. | This supports iterative review, but a revision request is not an approval record. A future study should establish how versions, reviewer identity, comments, and accepted changes are preserved. |
| **Connected apps and plugins** | Plugins/apps connect Work to sources such as email, file stores, chat, calendars, CRM, and project trackers. Users can select relevant plugins and direct a request to one by name. A connection uses the permissions of the authorized account; workspace admins can restrict availability and, where supported, limit actions or require confirmation. A shared/agent-owned connection can have different source permissions from the requesting user. | This could bring evidence from systems auditors already use, but source-system permissions, account identity, sync freshness, and action scope must stay visible. A connector being enabled is not itself proof that the auditor is authorized for every record or action. |
| **Skills and reusable workflows** | Skills are reusable instructions and optional resources/scripts for a task; apps/connectors provide access to external information or actions. Plugins can package skills, apps, or both. A skill can be invoked explicitly or selected based on its description; a skill itself does not add source-system access. | Standardized audit procedures may be reusable, but methodology ownership, version, approval, and scope need to be clear. Do not conflate a procedure instruction with evidence access or an approved work program. |
| **Plugin authoring** | When enabled in a workspace, users can describe a repeatable task, add instructions and reference material, then create or refine a plugin through conversation. A plugin can package skills and optional app connections; creating one does not grant new data access. | This captures repeatable workflows. Approval/version ownership and conformance with the audit methodology remain outside the documented plugin feature. |
| **Web search and browser** | Work can research public websites. The desktop built-in browser is distinct from the remote Cloud Browser and from a user's ordinary browser. Cloud Browser has a separate session and cannot see local tabs, extensions, history, saved passwords, or authenticated local sessions. New-site access can require approval; website approval and approval for a consequential action are separate. Browser interactions can be inspected through visible page/replay records, but those records are not a complete compliance export. | Useful for public criteria or external corroboration. Public evidence should be distinguished from internal evidence, and website permissions should not authorize sending a report or changing a business record. |
| **Computer and local app use** | In the desktop app, Work can use supported local apps/browser/files when available and authorized. OS permissions and workspace/device policies apply. In Local computer access with Work Cloud, cloud coordination can request steps from an online connected computer; the task must have been created after sync was enabled. | A public feature catalogue or Codex source review does not demonstrate desktop access in a future auditor-specific tool. Local access is a separate permission surface from cloud access. |
| **Computer Use boundaries** | Computer Use operates graphical apps through the desktop when enabled. Windows use takes over the active foreground session; macOS requires screen-recording and accessibility permissions. It cannot approve operating-system security prompts, authenticate as an administrator, or operate terminal apps or ChatGPT itself. Browser use can expose already signed-in sessions, so a connected browser and a desktop-app connection are distinct access paths. | UI automation can reach systems without a connector, but an auditor would need explicit app/task scope and review. Wrong-window interaction, signed-in identity, and consequential actions are material risks documented by OpenAI. |
| **Appshots** | Appshots are a separate desktop context handoff: they attach an image and available text from the frontmost app window to a ChatGPT conversation. Available on macOS and Windows, they require permissions where prompted; some apps may provide only visible screenshot content. An appshot is reviewed/shared like an attachment and is not itself a record of subsequent Computer Use actions. | Could help an auditor ask about a screen or app state. It may capture sensitive information and can omit off-screen or inaccessible text, so it should not be treated as a complete evidence export. |
| **Local and cloud execution** | Work may run locally or in the cloud depending on surface and settings. Cloud runs on OpenAI-managed infrastructure and does not automatically inherit local files, apps, browser sessions, or private-network access. With Work Cloud plus approved local access, cloud coordinates while individual steps can run on the connected computer. The computer must stay online for local steps. A task cannot change execution mode mid-turn; if the computer is unavailable, a later turn may continue in a cloud container without local resources or local execution policies. | Data location, tool availability, and policy enforcement depend on the mode. An audit-specific product would need an explicit record of which source/executor produced each result and should not infer device-only processing from a “local” label. |
| **Cross-device continuity** | Eligible cloud Work chats can sync across desktop, web, and mobile; users can continue a task or send follow-up instructions from another device. Local resource steps still require the connected computer to be online. Existing tasks do not automatically gain local access when sync is enabled later. | Review/steering may happen away from the workstation, but a reviewer should see whether an outstanding step depends on a connected machine or source that is unavailable. |
| **Scheduled tasks and monitoring** | Users can run a task once, on a time schedule, or in response to supported app events. A scheduled task can start a new chat per run or return to an existing chat/context. Event-triggered Work tasks support eligible Gmail incoming mail, Slack channel messages, and GitHub pull-request activity; event triggers and time schedules cannot be combined in one task. Availability and creation/edit controls vary by surface and workspace. | Potential use: refresh an audit status, monitor remediation updates, or prepare periodic evidence exceptions. A reminder/monitor should surface changes for auditor review; it should not autonomously close findings or certify remediation. |
| **Team Tasks** | In eligible Business/Enterprise workspaces, teams can own scheduled or event-triggered tasks that run in the cloud using a team service account and selected workspace or team connections. Permitted members can review runs and manage tasks; earlier runs and generated files may be visible to team members. Tasks do not inherit the creator's personal memories, custom instructions, or chat history, and an unattended task cannot finish a new app sign-in. A completed schedule does not prove its last run succeeded. | This is a shared-workflow capability, distinct from an individual auditor's schedule. Engagement confidentiality, membership changes, shared connection identity, run visibility, and separation between engagements would need investigation. |
| **Activity and notifications** | When available, Activity lists chats that are unread, running, or waiting for a response; filters vary by surface. Separate desktop notification settings control completion alerts and permission/question notifications. A floating pet can show Running, Needs input, Ready, or Blocked status, but those are pet indicators rather than Activity list statuses. | Helps users notice work needing input, but an alert is not a review queue or a formal sign-off. User-visible states and escalation behavior need confirmation. |
| **Voice** | Voice is available in supported Work surfaces. In the desktop app, a user can start or continue a task by speaking, check progress, and change direction; voice may also coordinate with supported existing threads. On supported macOS setups, screen context can be shared. Voice follows the selected task's tool permissions; approvals still require the supported interface and voice does not create new authority. | Voice could help with interviews or hands-free steering, but the public docs do not define audit interview recording, consent, transcription retention, or evidence protocols. |
| **Models and task effort** | Users select from models and options available to their plan/workspace. OpenAI recommends stronger reasoning/visual options for difficult tasks and lighter options for simpler work; longer tasks may use more usage/credits. Defaults do not grant access to unavailable features. | Model identity/version and output provenance may be useful context to show or export with generated work when a practitioner's methodology or receiving system requires it. They do not make this tool the authoritative record system. |
| **Personalization and memory** | Work can use ChatGPT memory and account/workspace personalization settings where available; some web drafting can use a user's writing style from connected apps if enabled. This differs from Codex's local memory store. Memory is a context aid, not a complete transcript or guaranteed source of required instructions; Team Tasks do not inherit personal memory or chat context. Separate optional macOS Computer History can turn activity across allowed apps/sites into timeline context; it is not an engagement record. | Persistent audit methodology and engagement facts cannot safely depend on hidden or personal memory. Research should establish which context enters a task and how a user can inspect or exclude it. |
| **Workspace access controls** | Admins can separately govern Work Cloud and Work Local for roles; Codex Local is controlled separately. App/plugin access, browser use, code/shell network access, and other capabilities have their own controls. Plan, rollout, and role permissions affect what a member sees and can do. | Least-privilege access and role-specific approval are fundamental if audit engagements contain restricted or privileged evidence. Work's own settings are not a substitute for designing an audit permission model. |
| **Action approvals** | App permissions can control whether Work asks before using an app, changing records, or taking important actions. Browser access, site permission, and consequential site actions are distinct approval points. A task can pause for user review/approval. Coverage varies by app/action. | Keep evidence collection, auditor judgment, report approval, and management communication separate. Do not assume every action is individually confirmed. |
| **Privacy, retention, and deletion** | Work data follows workspace policies, but conversations, transient uploads, project files, Library files, connected-app copies, memories, browser cookies, and compliance logs can have different retention/deletion rules. Deleting a chat, ending a task, clearing cookies, and retaining compliance records are different operations. | These are mandatory discovery topics before real audit data is used. A project/chat is not automatically the authoritative retained engagement file. |
| **Compliance/audit visibility** | For eligible Enterprise/Edu environments, supported Work prompts and responses are available through the Compliance Logs Platform; connected-app calls are logged separately, with some supported file records. Coverage is not a complete record of every hosted file operation, shell command, browser interaction, tool invocation, or approval. Compliance Logs Platform records have a 30-day retention period; organizations needing longer retention export supported records. Workspace analytics are for aggregate adoption, not an auditable record. | These Work logs are product telemetry/compliance records, not the destination system for an auditor's engagement or evidence. Research whether useful provenance, approval, or run metadata can be shown/exported so practitioners can place outputs in the systems they already use. |

## Two complementary product studies

The user-supplied product hypothesis is to study ChatGPT Work's task workflows together with Codex's agent capabilities and operating model, then identify what an auditor-focused tool might adapt, modify, or add. The product should be tailorable across internal audit, external audit, advisory, IT/IS audit, industries, and methodologies. The user has specified two modes: work with the practitioner's existing system of record, or use a built-in Diligent-like audit record system. This is a research lens for scouting; it does not select a design or architecture.

| Study stream | Current evidence | What this stream can establish | What it cannot establish |
| --- | --- | --- | --- |
| **ChatGPT Work workflow** | This catalog's Work inventory and official Work documentation. | User-facing Work tasks, sources, controls, progress, outputs, and available workflow patterns. | Work's private implementation or behavior not documented for the observed account/surface. |
| **Codex capabilities and operating model** | [Codex capability catalog](CODEX_CAPABILITY_CATALOG.md), official Codex documentation, and public `openai/codex` source. | What Codex clients and the released public harness do, how the runtime/protocol is structured, and which behaviors vary by surface. | That Work uses the same implementation, or that the open repository contains every Codex client, hosted service, or model component. |
| **Comparative agent products** | [Claude Code crosswalk](CODEX_CLAUDE_CODE_CROSSWALK.md) and [Claude Cowork catalog](CLAUDE_COWORK_CATALOG.md), using official Anthropic documentation and its public released materials. | How a developer-focused agent and a knowledge-work surface handle capabilities also found in Codex/Work, and where approaches differ. | That another vendor's feature is better, that public extension materials are product source code, or that a product's behavior is universal across accounts and plans. |
| **Auditor-specific adaptation** | The IIA lifecycle crosswalk below as one internal-audit example, plus public evidence on tailoring instructions, skills, tools, integrations, and outputs. | Which product concepts are common across audit/advisory work, and which should be configurable for a practice area, industry, team, and methodology? How should work and records move in external-system and built-in-record modes? | A single baked-in methodology, industry, review chain, or mandatory record-ownership mode. |

At a high level, the user's idea is not just to copy Work as-is: it is to evaluate Work's work-oriented task flow alongside Codex's complete capability set, agent runtime, execution, tools, state, clients, and extensibility. Claude Code is the developer-tool comparison; Claude Cowork adds a separate knowledge-work comparison. These are evidence streams for later planning, not design decisions. The detailed Codex feature list and public implementation map are in [CODEX_CAPABILITY_CATALOG.md](CODEX_CAPABILITY_CATALOG.md).

## Mapping to the internal-audit lifecycle

This is a workflow crosswalk, not an implementation plan. It uses the IIA's 2024 Global Internal Audit Standards as one illustrative internal-audit reference; CAE means chief audit executive. It is not a universal audit/advisory workflow or an assumption that every practitioner uses IIA standards. Other practice areas and methods should remain adaptable.

| Internal-audit work | Relevant Work capabilities | 2024 IIA standards lens | Research implication (not a design decision) |
| --- | --- | --- | --- |
| Engagement communication, risk assessment, scope, criteria, resources | Projects, task prompts, connected sources, reviewable summaries, follow-up prompts | Standards 13.1–13.5 cover communication; risk assessment of activity objectives, risks/risk tolerance, prior assessment, GRC/control processes, and fraud risks; assurance/advisory type; objectives, scope, period, and limitations; criteria adequacy; and resource types/quantity. CAE approval is required for objectives/scope and changes. Scope limits are discussed with management and unresolved limits elevated to the board. Inadequate criteria are resolved through discussion with the board and/or senior management. If resources are insufficient, auditors discuss concerns with the CAE; implementation guidance says the CAE discusses implications with senior management and the board. | Later study should learn how an auditor records the approved engagement boundary, risk assessment, criteria, and any scope/resource change. |
| Work-program creation and approval | Outcome prompts, generated documents/spreadsheets, progress steering, approval pauses | Standard 13.6 ties program criteria, tasks, methods/tools, and auditor assignments to engagement objectives. The CAE approves before implementation and approves changes. IIA implementation guidance says a sampling program should document the sampling method, population, sample size, and whether results can be projected; Standard 14.6 addresses documenting population/sample details in workpapers. | A generated procedure list is not by itself an approved work program. Learn how approval, revisions, and sampling choices are currently recorded. |
| Fieldwork and evidence collection | Files, connected apps, browser, Computer Use, data analysis, task threads | Standard 14.1 requires relevant, reliable, and sufficient information. Reliability is strengthened by direct/independent sourcing, corroboration, and effective source-system governance. | Learn what source, date, extraction method, population, sample, transformations, and evidence limitations auditors must retain to reproduce work. |
| Analyses and potential findings | Data analysis, web research, generated tables/charts, source-linked drafts | Standard 14.2 requires analysis of relevant, reliable, sufficient information and comparison of criteria with the existing condition to identify potential findings. If more analyses are needed, the work program is adjusted and approved by the CAE. | Distinguish source facts, calculations, inferred explanations, and auditor conclusions; flag missing evidence rather than filling gaps. |
| Finding evaluation and action plans | Iterative review, draft findings, connected apps, generated artifacts | Standard 14.3 evaluates each potential finding's significance, considers likelihood/impact, collaborates with management on root cause/effects, documents and communicates significant risk as a finding, and prioritizes findings under CAE methodology. Standard 14.4 determines recommendations/actions to resolve criteria-condition gaps, mitigate risk, address root cause, or improve the activity; disagreements require an established method for both parties to express positions/rationale and determine resolution. Management remains responsible for corrective action; names and due dates are explicit final-communication information under 15.1. | Learn reviewer and management-response steps, disagreement handling, and risk-acceptance authority. |
| Engagement conclusion and documentation | Reviewable workpapers, chat history, project context, approvals, file versions | Standard 14.5 summarizes results relative to engagement and management objectives and professional judgment on aggregate finding significance; assurance conclusions judge governance, risk management, and/or control effectiveness, including when effective. Standard 14.6 requires reperformable documentation; auditors/supervisors review accuracy, relevance, and completeness; the CAE must review and approve it. | Chat or task completion is not a reperformable workpaper. Learn required preparer/reviewer attribution, evidence linkage, retained versions, and approval evidence. |
| Final reporting | Reviewable documents and presentations; progress steering | Standard 15.1 requires final communication of objectives, scope, recommendations/action plans if applicable, conclusions, and responsible parties/target dates. Assurance communication also includes finding significance and priority, scope limitations, and a conclusion on governance, risk management, and control effectiveness. The CAE reviews/approves before issuance and determines dissemination. Acknowledge completed actions and disclose Standards nonconformance when applicable. | Identify which outputs are drafts, who approves final language, how distribution and management response are recorded, and what nonconformance disclosures apply. |
| Remediation follow-up | Scheduled/event-triggered tasks, connected apps, reminders, run review | Standard 15.2 calls for inquiry about progress, risk-based follow-up to confirm implementation, and status updates in an action-tracking system. Follow-up extent considers finding significance. If agreed dates are missed, auditors document management's explanation and discuss with the CAE. The CAE determines whether delay/inaction is risk acceptance beyond tolerance; communication of accepted risk follows Standard 11.5. | A notification or event summary can cue a human check but does not prove implementation or close a finding. Learn evidence and escalation rules. |
| Quality review, retention, and audit trail | Projects, Activity/notifications, workspace controls, Compliance Logs Platform exports | Standard 12.3 requires CAE methods for supervision, quality assurance, and competency development; engagement guidance; checks for complete programs and workpapers supporting results; conformance to Standards/methodology; auditor performance feedback/opportunities to improve; and documented, retained supervision evidence. CAE retains ultimate responsibility if supervision is delegated. Standard 14.6 separately requires documentation review/CAE approval and retention under applicable policies. OpenAI describes compliance records with limited coverage and retention, not a complete action trail. | Compare external-record mode (authoritative records remain in connected systems) with built-in-record mode (native engagement records, approvals, retention, and audit trail become product responsibilities). Define export, lineage, review attribution, retention, and legal-hold needs for each. |

## What we cannot infer from the sources

- We cannot see Work's private source code or claim that the public Codex repository implements it. The public Codex repository is still directly useful evidence for Codex's own harness, clients, protocols, and capabilities; see [CODEX_CAPABILITY_CATALOG.md](CODEX_CAPABILITY_CATALOG.md).
- The docs are not a stable screenshot-level specification; exact UI layout and feature availability may vary by plan, platform, role, and rollout.
- Public documentation does not establish that Work or Codex is designed for every audit/advisory practice, industry, or methodology. It does not prescribe how generated outputs integrate with a practitioner's existing system of record or how a built-in audit record mode would work.
- A Work task completing does not itself prove the task achieved its objective or that output was delivered; users are told to inspect results and errors.
- We have not observed a live engagement in a logged-in Work workspace, connected any internal source, or used confidential audit data.
