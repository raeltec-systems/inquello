### Full access: confirmed missing native Windows resolver
- Exact failure at tool-bounds-integration.test.ts:288: PowerShell visibility command is refused because it needs permission under never, with no command rule matched.
- `inquello_processor.rs:1279-1329` implements resolve_program only under cfg(unix); cfg(not(unix)) returns None for EVERY program. Full access correctly selects host resolution (`ExecPlacement::BoundedGuest::resolve`, lines 1386-1391), not the guest.
- `command_rules.rs:474-508` makes unresolved programs Prompt regardless of default allow, then Forbid if asking behavior cannot prompt. With no rule and a resolved program, never would allow; the observed reason therefore directly follows unconditional unresolved Windows-host lookup.
- This is a production capability gap in native Windows executable resolution exposed by a valid Full access reach witness, NOT evidence that broad mode is specific permission or approval, and NOT a reason to add an allow rule. An allow rule cannot legitimately override unresolved identity anyway. Guest refresh cannot fix this native branch.
- Spec 1.20 lines 209-220 explicitly preserves unresolved=>prompt/refusal and guest-only resolution for bounded Windows. The later guest work did not implement native Windows lookup. Repair must implement actual Windows spawn-compatible identity resolution (absolute/relative paths, executable lookup semantics, canonical identity and aliases), retain fail-closed ambiguous/unresolved handling and command-rule precedence, then keep this reach assertion. No such repair was made here.

### Alias refusal: unresolved observation plus a definite fixture portability issue
- Exact final diff at permissions-integration.test.ts:241 shows only ok:true, omitting result fields; it does not show which loop value failed or whether the command exit code was successful. Do not call this proven command execution or a proven bypass based on ok:true alone.

The bounded executor resolves/executes guest paths, with host mounts inaccessible. That alias is not a guest alias. The later host-created `true` -> `/usr/bin/touch` trick has the same mismatch. A valid WSL symlink witness must construct the synthetic alias inside that Task's guest filesystem and invoke its guest path, while preserving all forbid/prompt/allow and no-write assertions. Do not merely delete/skip the alias assertion or mount host storage to satisfy it.

Current host matching compares resolved command identity to both original and resolved rule head; fake Ubuntu guest tests cover those forms (`inquello_processor_tests.rs:2575-2660`). Actual guest identities were not measured in this assignment.

Therefore stale guest source or failed queries alone do not explain ok:true without additional evidence. Guest source parity remains important, but matching only exec-server/src/lib.rs does not establish parity of server/file_system_handler.rs, sandboxed_file_system.rs, local_file_system.rs or URI code used by these queries.
