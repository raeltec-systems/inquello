### Story 1.10b: the always-run refresh test does not detect losing rotated credentials on disk

- **Changed surface:** successful refresh replaces both credentials and persists the replacement at `desktop/src/main/identity/session.ts:419` and `desktop/src/main/identity/session.ts:427`.
- **Impacted consumer or site:** desktop startup constructs a new vault/session at `desktop/src/main/identity/index.ts:46`; `IdentitySession` reloads the saved record at `desktop/src/main/identity/session.ts:154`. That next process depends on the rotated pair having reached the vault.
- **Existing test evidence:** `Broken-verification gap`. The ordinary unit test at `desktop/test/identity-session.test.ts:205` checks successful in-memory refreshes and the fake service's rotation state. Its disk assertion at line 215 searches the encrypted file bytes for the old *plaintext* access credential; the old encrypted file already satisfies that assertion. It never reloads the vault or restarts the session after rotation. The meaningful decrypted-file assertions at `desktop/test/identity-integration.test.ts:120` do catch this regression, but the entire integration suite is skipped without a database URL at line 86. Repository-wide source searches for `refreshNow`, `runRefresh`, `identity/session` and `identity/vault` located these suites and the direct consumers; the smoke identity probe at `desktop/src/main/smoke-probe.ts:869` signs in and out without testing persisted rotation.
- **Missing verification:** in the always-run session suite, decrypt/reload the vault after refresh and assert that both saved credentials equal the new pair; recreate the session and assert it can authenticate using that record.
- **Demonstration:** in a disposable copy at `/tmp/inquello-verification-refresh-mutation`, removed only the `this.persist()` call in `runRefresh()` and ran the existing full `test/identity-session.test.ts`. All **27 tests passed**. Exact output is saved at `/tmp/inquello-refresh-mutation.out`. The repository source was not edited. PostgreSQL-backed integration tests were unavailable in this review environment, matching the suite's explicit skip condition.
- **Consequence:** a regression that leaves the old encrypted refresh credential on disk passes the default unit verification; restarting the desktop then reuses a rotated credential, causing the family to be revoked and requiring sign-in again.
- **Disposition:** `patch` — extend `rotation replaces both credentials, and concurrent refreshes are serialized` in `desktop/test/identity-session.test.ts` with a decrypted vault reload and a new-session authentication assertion. This needs only the existing fake issuer/service and real vault.

## Other findings

- **Story 1.12 — exports follow classified file symlinks into private/excluded data.** `desktop/src/main/data/inventory.ts:75` uses `lstat` but records symlinks as ordinary `HeldFile` entries. `desktop/src/main/data/export.ts:187` passes the classified link path to `copyWithDigest`, whose `fs.promises.open(source, 'r')` at line 93 follows the link. Reproduced with a harmless external sentinel file and `runtime-home/sessions/linked-secret.jsonl` pointing to it: the inventory labels the link `task-history`, then export succeeds and contains the external sentinel. Exact output: `{"inventory":[{"rel":"sessions/linked-secret.jsonl","category":"task-history"}]}` followed by `{"exportSucceeded":true,"privateSentinelCopied":true,"sourceOutsideGovernedRoots":true}`. Reproduction: `/tmp/inquello-repro-export-symlink.cjs`; output: `/tmp/inquello-repro-export-symlink.out`. The export exclusion assertion at `desktop/test/data-operations.test.ts:102` uses regular fixture files, so it does not exercise this bypass. This is an observed defect, not a hypothetical verification gap.

- **Story 1.13 — deleting a memory-only Claude API key through Local data leaves the key usable.** `desktop/src/main/data/service.ts:287` deletes only classified files via `deleteCategories`; `desktop/src/main/data/delete.ts:100` removes files, while `ClaudeKeyVault.load()` at `desktop/src/main/providers/claude-vault.ts:91` reads the retained private memory record when OS storage is unavailable. `DataService` has no provider-vault hook, and main wires none at `desktop/src/main/main.ts:319`. The same vault's explicit `clear()` would remove that record at `claude-vault.ts:127`, but Local data never calls it. Reproduced using the compiled real `DataService`, `ClaudeKeyVault` and `ProviderService`, with `basic_text` backend and a synthetic key: `before={"state":"stored-unverified","storage":"memory-only"}`; deletion returned `ok:true` and `filesRemoved:0,filesRemaining:0`; afterwards `stillHeld:true`, and a subsequent verification invoked the fake verifier and returned `verifyAfterDelete:true,checkCalls:1`. Full output: `/tmp/inquello-repro-memory-delete.out`; script: `/tmp/inquello-repro-memory-delete.cjs`. The memory-only test at `desktop/test/providers-units.test.ts:118` invokes `vault.clear()` directly, and the Local data test at line 629 only checks accepted/deletable category IDs. Neither checks this actual cross-service action.

- **Stories 1.6–1.8 — the contrast evidence assertion fails on harmless floating-point serialization differences.** `desktop/test/contrast.test.ts:194` compares the entire generated JSON string exactly, including unrounded ratios (`evidence()` at line 29). The parent review's full desktop run observed the failure on values such as `8.99580851260002` versus `8.995808512600018`, while contrast thresholds and pass/fail outcomes were unchanged. This is test portability, not a contrast failure. A numerical comparison/tolerance for ratios would preserve the threshold checks without rejecting an otherwise equivalent run.
