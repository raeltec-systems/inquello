## Coaching fork inspected — domain boundary

The following alternatives were evaluated to prepare coaching. During this source pass, the user selected **AD1: fork** and **AD2: retain the Codex runtime plus app-server, with audit-specific logic in Inquello modules and focused core changes where needed**, as relayed by the parent. That decision selects the direction; it does not select the implementation commit, desktop framework, protocol topology, hosted services or deployment model. The alternatives remain below to explain the source-supported boundary, not to reopen the decision:

1. **Compose around core through app-server.** Keep audit concepts, review/approval records, integration verification and product workflow in an Inquello layer while using thread/turn/item and execution APIs underneath. This gives a defined protocol boundary and could reduce changes inside the engine. It still requires mapping domain state to runtime events, application identity/policy integration, and testing whether required extension/control paths are exposed. It does not settle local versus hosted execution.
2. **Use the Rust facade/extensions, with selective deeper integration only where needed.** Host ThreadManager through core-api and install suitable contributors or a ThreadStore implementation; change core internals only for a demonstrated unmet invariant. This offers access below the wire boundary but increases Rust/upstream coupling and testing obligations. It does not require turning all audit entities into conversation-history items.
3. **Embed audit concepts deeply in core and persistence.** This could make domain invariants part of runtime operations where an external layer cannot enforce them, but risks coupling professional authority and business records to conversation/model-loop machinery. No inspected code proves that this depth is necessary. Decide only after concrete requirements defeat the first two seams.

**Next coaching boundary:** desktop workbench with organisation-managed coordination and an allowed unattended runner versus a primarily hosted operating model. The decisive scenario is what runs when the user's computer is off. This source pass establishes reusable execution interfaces and local runtime persistence, but not the complete hosted coordination or scheduler backend for either option. Hosting, durable scheduling, identity/mandates, trigger intake, ownership/reassignment and uncertain-effect recovery still need explicit supply routes. No cloud vendor or protocol topology is chosen here.
