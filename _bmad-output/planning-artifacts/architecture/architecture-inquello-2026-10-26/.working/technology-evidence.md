## Electron boundary: supported mechanism, untested integration

Electron's main process has Node APIs; renderers use web tooling. Context isolation separates preload from page globals. The documented bridge pattern exposes a specific method for each permitted IPC operation rather than generic IPC access. Electron also recommends renderer sandboxing, IPC-sender validation, restrictive content policy and limits on navigation. These mechanisms support a narrow React renderer → typed preload bridge → privileged main boundary. TypeScript types do not validate untrusted messages at runtime. [Process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation), [security](https://www.electronjs.org/docs/latest/tutorial/security)

Main-owned `child_process.spawn` can launch the Rust app-server and manage its stdin/stdout. Official Codex documentation directly demonstrates this Node/TypeScript pattern: newline-delimited protocol messages, initialization and streamed notifications. It also says generated schemas match the generating Codex version. Keep stderr separate from protocol output; process errors, stream backpressure, shutdown, restart and interrupted/uncertain work need implementation checks. `utilityProcess.fork` launches a Node script and does not support writable child stdin; it is not a direct Rust-stdio substitute. [Codex app-server](https://learn.chatgpt.com/docs/app-server), [Node child processes](https://nodejs.org/api/child_process.html), [Electron utility process](https://www.electronjs.org/docs/latest/api/utility-process)

**Support caveat:** the same Codex page's remote Code Mode host section says the app-server command and WebSocket transport are experimental/unsupported for production; its protocol section separately labels WebSocket experimental and lists stdio as default. Record this wording/context rather than deriving a blanket production-support guarantee from protocol availability. Electron renderer isolation also does not supply the Rust agent sandbox or Inquello professional authority.

## Rust modules and domain persistence: structural fit

Rechecked the previously observed main revision **`efab30992b28bb8fc5064dbac9c12090b8818e98`**, not a newly selected fork base. Its Cargo workspace already separates app-server, core/core-api, extensions, state, rollout and thread-store crates; workspace edition is 2024 and toolchain is 1.99.1. Cargo permits additional member crates but shares dependency resolution and a lockfile. **Inference:** separate Inquello domain crates fit this structure without requiring audit entities inside the model loop; crate membership does not determine process boundaries. [Workspace lines 1–176](https://github.com/openai/codex/blob/efab30992b28bb8fc5064dbac9c12090b8818e98/codex-rs/Cargo.toml#L1-L176), [toolchain](https://github.com/openai/codex/blob/efab30992b28bb8fc5064dbac9c12090b8818e98/codex-rs/rust-toolchain.toml#L1-L3), [Cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html)

ThreadStore explicitly separates canonical history appends from metadata updates; LocalThreadStore uses rollout JSONL and SQLite metadata. Its contract is unchanged from the research pin. The state crate describes a rollout-metadata mirror, not an Inquello domain authority. **Inference:** domain-owned persistence behind an explicit module boundary is compatible with these responsibilities; it need not modify upstream tables or replace ThreadStore. [ThreadStore contract](https://github.com/openai/codex/blob/efab30992b28bb8fc5064dbac9c12090b8818e98/codex-rs/thread-store/README.md#L3-L35), [state scope](https://github.com/openai/codex/blob/efab30992b28bb8fc5064dbac9c12090b8818e98/codex-rs/state/src/lib.rs#L1-L10)

The adopted separate local SQLite working-metadata store still needs explicit identifiers/version links, migration ownership and recovery/reconciliation across runtime and domain writes; no cross-store transaction or tamper-evident ledger is established here. SQLite adoption does not make V1 external records native Inquello records. No driver version, physical file layout or shared service is selected by this evidence check. The existing [source map](upstream-architecture.md) retains the broader evidence boundaries.

Final independent verification on 2026-10-27 identified a persistence compatibility floor: the [observed upstream state crate](https://github.com/openai/codex/blob/efab30992b28bb8fc5064dbac9c12090b8818e98/codex-rs/state/src/lib.rs#L7-L10) asserts SQLite 3.51.3 or later for the WAL-reset corruption fix. [SQLite's explanation](https://www.sqlite.org/wal.html#walreset) also identifies fixed backports. Verify the actual runtime resolved by Inquello's separate domain driver contains the fix; an upstream assertion does not verify that independently linked runtime. This is an implementation gate, not selection of a driver or a claim that a build has passed.
