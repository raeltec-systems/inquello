## 1. Direction and alternatives

| Choice | Recommendation and consequence | Alternative not selected |
| --- | --- | --- |
| AS-SVC1 authentication | An OIDC identity provider performs authentication; Inquello owns stable principals, app sessions, Workspace membership, roles and grants. Provider sign-in for inference remains independent. Avoid storing passwords in Inquello. | Building password/MFA/recovery infrastructure adds security ownership; using ChatGPT/Claude login as product authority violates the adopted boundary. An identity supplier still needs selection before production integration. |
| AS-SVC2 shared authority | One logical service using the shared Rust domain, PostgreSQL transactional metadata, private blob storage and a versioned HTTPS JSON contract. | AS-SVC3 handoff | Upload only selected immutable artifacts and permitted relied-on context into a service-controlled transfer area; exact-version materialization on the recipient desktop. | Sender-local links fail when their computer is offline. | AS-SVC4 connectivity and revocation | Cloud-model agent work needs a working model connection, private or shared. Shared-derived use additionally requires live Inquello authority. ## 2. Identity and session contract — SC-1

- The desktop is a public native client. It launches an external system browser for Authorization Code + PKCE S256; no embedded login webview and no packaged client secret. Bind callback to the initiated login using state, nonce, redirect URI and PKCE verification. The issuer/redirect allowlist belongs to deployment configuration, never model output.
- Validate issuer, signature/key, audience, expiry, nonce and flow binding before mapping `(issuer, subject)` to an immutable `principal_id`. Email/display name are mutable attributes, not authority or automatic account-link keys. Linking identities requires an authenticated, explicit recovery/linking flow; never merge accounts by matching email.
- Bootstrap is its own pre-Workspace protocol, not an ordinary authenticated command. The service creates an expiring, one-use login transaction with nonce and allowed issuer/client/redirect binding; the native host owns the PKCE verifier and browser state. After exchanging the code at the issuer, the host submits the ID token and login-transaction proof to Inquello. The service independently validates the signed token, expected issuer/audience/authorized-party, expiry and its transaction nonce; it never trusts a desktop-parsed claim. Atomically consume that transaction and create the session. Token replay or transaction mismatch fails. If the credential response is lost, do not replay bootstrap or expose its credentials through receipts: abandon/revoke that pending session through the bound login transaction and perform a new sign-in.
- Inquello creates a server-held session record: `session_id`, `principal_id`, `device_id`, issuer subject reference, created/last-authenticated time, expiry, revoked time and refresh-family identifier. Desktop receives an opaque short-lived access credential and rotating refresh credential. Numeric lifetimes are configurable security-policy values, selected before real-data enablement; correctness never relies on expiry alone.
- Keep credentials in the trusted host's OS-backed credential store with process/sandbox access boundaries verified on each supported host. Encryption or OS storage alone does not prove isolation from arbitrary same-user subprocesses; unsupported hosts/routes remain gated. Renderer, model, arbitrary tools, subprocesses, URLs, artifacts and logs receive no raw credential. A session credential is not permission to every Workspace.
- Every shared request resolves the service session and current principal/Workspace membership. Global principal and session records have revocation revisions; transaction locks always follow principal → session → Workspace authorization epoch → resource order. Session/logout/principal revocation serializes against that same authority check, including reads and mutations; it emits durable principal/session invalidation as well as any applicable Workspace event. Refresh rotates atomically; reuse of an already rotated credential revokes that refresh family and requires sign-in. Concurrent refresh is serialized by the desktop host. Refresh is not an ordinary receipt-replay command: never store/recover raw refresh/access credentials in general operation receipts. If its response is lost or outcome uncertain, the client discards that family, invokes the bounded family-revoke endpoint using its existing credential if still valid, and requires fresh sign-in; reuse is not silently retried. Any remaining inaccessible session remains unusable to this client and follows server expiry/revocation policy. Logout/device revocation disables the service session and invalidates active shared runs; it does not erase exports or revoke separate inference-provider accounts.
- Membership response supplies displayable role/membership revisions, not an offline authorization token. Unknown issuer, invalid state, expired/revoked session, disabled principal, missing membership, unsupported contract or unavailable authority results in blocked shared work. An unavailable model connection prevents further model-dependent agent work in private and shared Tasks. Local storage/tool execution does not imply local inference. A service-only outage and a model outage are different dependencies; private work cannot be promised to continue unless its actual model connection and all applicable authority/runtime requirements remain satisfied.
- Workspace creation and first administrator are explicit service bootstrap commands under an authorized operator, not a public self-elevation API. Invites bind a Workspace, intended identity and least-privilege roles; acceptance requires authenticated identity and authorized grantor. Invitation expiry/replay is validated; no guest role is introduced. Administrator membership management does not grant access to private Tasks.

## 3. Common protocol and mutation authority — SC-2

A single versioned contract package owns wire schemas and conformance fixtures for service, Rust clients and desktop bindings. It is defined before those units are built independently. This contract fixes semantics; generated schema files are implementation deliverables, not supplied code.

- Transport: HTTPS JSON under `/v1`; authenticated content streams use the same service authority. Protocol major changes require explicit client capability negotiation; unsupported major versions fail closed. Optional display fields may evolve compatibly; unknown authorization actions or policy semantics are denied, not ignored.
- IDs are opaque UUID strings, scoped by explicit `workspace_id` where applicable. Times are UTC RFC 3339, revisions monotonically increasing integers serialized as decimal strings, digests SHA-256 lowercase hexadecimal over exact bytes. Never equate a digest with authenticity or evidence sufficiency. IDs/digests must not be used as access capabilities.
- SC-2 envelopes apply after an authenticated Inquello session and Workspace exist; SC-1 defines bootstrap/refresh separately. Session-management operations are principal-scoped with no invented Workspace ID; grant/content operations are Workspace-scoped.
- Mutation envelope: `command_epoch`, `operation_id`, `workspace_id`, `expected_revision`, `schema_version`, typed `payload`. Actor/session is resolved from credentials, never trusted from a client-supplied actor field. Service response: `operation_id`, `resource_id`, resulting `revision`, `authorization_epoch`, `status`, `receipt_id`. Service capability negotiation supplies the current command epoch; an old/unknown epoch is rejected for new mutations, never treated as a fresh operation. A draft includes `expected_revision=0` for creation; other writes require the observed revision.
- Durable receipt key is `(principal_id, scope_kind, scope_id, operation_id)`, where scope is the principal for session management and the Workspace for content commands, with canonical request digest. Exact retry returns the recorded outcome only after checking present access to the returned content; same key/different payload conflicts. An unavailable/unknown outcome prompts receipt lookup, not a new operation ID. Receipt content is redacted if access has changed. No receipt creates eternal read access.
- Service authorizes and compares expected revision in the same metadata transaction as the mutation and audit/outbox write. Authorization-policy changes and dependent mutations use the same Workspace authorization-epoch lock/order; after a revocation commits, a later operation cannot commit using its old snapshot. Serializable failures may retry the bounded transaction using the same operation ID, not repeat external effects.
- Errors: unauthenticated, denied, version conflict, unsupported contract, incomplete material, dependency unavailable, uncertain outcome. Error details never confirm existence or names of inaccessible resources. Conflicts preserve the local draft and require reload/review; never last-write-wins.
- Local SQLite owns private working records; the service owns shared registrations, membership/grants, submissions and coordination. Client cache revisions are observations only. A Task remains locally owned; this contract does not add multi-writer Task replication or automatic local-to-cloud execution.

## 4. Shared data and grant model — SC-3

| Record | Minimum interoperable fields and owner |
| --- | --- |
| Workspace/member | Workspace kind (`internal_company` initially enabled), principal, membership status, role bindings, policy reference, revision; service-owned. Engagement membership is distinct and cannot expose private Tasks. |
| Shared resource | Workspace, resource ID, kind (`artifact`, `folder_manifest`, `review_package`, `task_package`), creator, origin Task/Engagement reference, registration state, revision; service-owned registration, not a formal V2 record. |
| Resource version | Immutable version ID, resource ID, manifest digest, byte size/media type, originating artifact revision and reviewed-basis ID, created-by/time; no mutable latest pointer in a submitted basis. |
| Grant | Grant ID/revision, Workspace, resource/version or declared folder scope, audience (`principal` or `workspace_audit_team`), actions, issued-by, active/withdrawn state and policy revision. External/guest audience is rejected in V1. |
| Reviewed basis | Basis ID/digest, exact artifact versions, evidence/extract references, Method/version/parameters/departures, coverage/exclusions, policy IDs/versions/effective period, limitations and predecessor basis. A context-only change creates a new basis. |
| Coordination | Submission ID, basis ID, recipient, note IDs/anchors, per-note disposition and human-selected decision attribution; separate from each preparer's/reviewer's private Task and from external formal acceptance. |
| Lineage | Derived object/version, conjunctive source-version dependencies, admission event, originating engagement/period/status and applicable policy references; service checks grants at use, not just indexing. |
| Operation/event | Durable receipt plus monotonic event cursor, affected IDs, authorization epoch, outcome and safe diagnostic category. No source content or credentials in notifications. |

Effective access requires active session, active Workspace membership, enabled Workspace kind/route, applicable policy, and at least one current grant for the exact object/version/action. Resource creator rights remain policy-controlled; role labels are not universal resource grants. Candidate actions are `read`, `derive`, `comment`, `submit_review`, `issue_notes`, `share`, `export`; `manage_membership` is a distinct administrative operation. Professional acceptance is a human command with separate applicable authority, not an implicit `comment` or reviewer-role permission.

Each action checks both the target grant and applicable lineage rights: `read` needs permitted source-derived disclosure, `derive` needs source processing permission, `export` needs export permission for every included dependency, and `share` needs delegable rights for the proposed audience/actions on every dependency. For this first contract, absence of a required dependency action denies the whole combined object; no inference from `read` to `export` or `share`. A grant cannot exceed the issuer's delegable rights; sharing a derivation cannot launder access to protected source dependencies. Team-share is an explicit Workspace-audit-team audience grant. An individually shared review package is not automatically company-wide knowledge. Formally issued work becomes eligible for institutional memory through an authorized issue event and its declared audience; issue cannot manufacture forbidden source rights. Another valid grant may preserve exact content/action access after one grant is withdrawn.

Folder sharing is an explicit logical manifest, not a filesystem watcher. The derived default shares the enumerated registered versions only. An explicitly chosen “include future registered versions” folder grant can cover subsequent deliberate registrations in that folder; it never uploads new local files automatically or admits a private conversation. Moving an item out removes the inherited route, while independently valid grants survive. Show this distinction and external-copy limits in the confirmation.

## 5. Upload, share and recipient materialization — SC-4

1. **Draft:** Creator selects files/versions, recipients/actions and allowed evidence/Method/coverage/policy context. The client shows inclusions, omissions, copy/retention consequences and inaccessible source dependencies. Do not silently include private Task messages. Local draft creation is not shared publication.
2. **Prepare:** Service checks current sharing rights and creates a bounded `upload_id` with workspace-scoped quarantine identifiers and expected digests/sizes. The prepare command and final commit command each have their own immutable operation ID/payload/receipt and both refer to this upload ID; chunk writes use `(upload_id, chunk_index, digest)` idempotency. A different body for an existing chunk or command key conflicts. Upload ID is workflow correlation, never reused as both commands' operation ID. Unpublished blobs have no recipient visibility or memory eligibility. Arbitrary client storage paths and cross-tenant object keys are rejected.
3. **Transfer:** Desktop streams selected bytes through authenticated service endpoints. Record acknowledged chunks/offsets and checksums to support interrupted transfer. Reusing the upload ID and identical chunk keys resumes verified bytes; changing bytes starts a new version/digest, not corruption of an existing upload. Media/content validation and quarantine handling precede safe previews; no active document execution in the service.
4. **Commit:** Service verifies complete blob availability/hash and the manifest's authorized lineage, compares expected revision and current rights, then atomically records the immutable resource version, grant, operation receipt and outbox event. Publication is technical shared registration, never Professional Approval. If commit outcome is unknown, query the commit command's operation receipt, not the prepare receipt. Orphan staging objects expire under an explicit cleanup policy and cannot be indexed.
5. **Retrieve:** Recipient requests exact resource/version using authenticated service; service checks current access, not a bearer URL. It streams only authorized components, rechecking between chunks and at completion; partial/revoked streams are discarded or quarantined by the client. No direct public or reusable presigned download link is provided in this first contract.
6. **Materialize:** Trusted client writes a separate controlled cache path, verifies digest/size/version and marks usable only after final current-access validation. Preserve an existing local edited file; never overwrite it on download. Opens the submitted version, not whichever file is newest. Manifest components distinguish `authorization_dependencies` (mandatory for any permitted disclosure/use of the containing derivation) from `review_context` (needed for sufficiency/reperformance but not necessarily a disclosure prerequisite). A denied/unknown authorization dependency blocks the containing object, never a partial bypass. Missing authorized review-context components can permit the artifact to open with explicit incomplete-review status; prohibited context is not transferred. Full review cannot be claimed. This classification is policy/domain-validated, never chosen by an untrusted author to bypass lineage.
7. **Use/revise:** Trusted workbench and tools use scoped materialization handles, not unrestricted cache directories. Reviewer Task remains private and anchors to submission/basis. Notes issued by a human are new coordination events; preparer revision creates a new artifact/basis and submission. Rechecks include source, Method, policy and coverage changes even when artifact bytes match.

A first artifact can be shared before full review coordination exists; its manifest uses currently available artifact/evidence fields and marks unavailable context. Later reviewer workflow adds its fields when introduced. No story requires future UI or memory infrastructure simply to test the earlier upload/access contract.

## 6. Revocation and active work — SC-5

The enforcement promise is **no later protected operation after revocation is committed**, under service transaction ordering, plus fail-closed desktop mediation at protected boundaries. It is not instantaneous remote erasure, cancellation of already transmitted provider work or a zero-latency guarantee.

- A membership/grant withdrawal transaction increments the Workspace authorization epoch, updates authority, records a durable invalidation event and returns a receipt. Read/derive/export/share/coordination requests serialize their authorization decision with that epoch. An earlier already-authorized disclosure may have crossed the boundary before revocation; report it as already transmitted rather than roll it back on paper.
- A live event stream supplies ordered epoch/cursor notifications to active clients. It accelerates invalidation but is not the sole security check. The trusted host maintains monotonic highest-seen principal/session/Workspace revocation revisions and a local connection generation. A disconnect/invalidation advances the local fence immediately. Authority requests and run steps capture that generation; delayed responses from an earlier generation or below any observed revision are discarded, even if they say allowed. Cursor gaps or reconnect require a new current snapshot and explicit run revalidation before resuming shared use; old responses cannot unfreeze the run. No event payload includes protected evidence text.
- Before every protected source read, tool/model dispatch, resumed run, output presentation/persistence, export or consequential effect, the host obtains current authority for the exact lineage/action from the service. Buffered output is not shown or stored as usable until its current check passes. No offline authorization lease is accepted.
- An active run tracks source/version lineage and the checked epoch. On withdrawal or lost authority channel, freeze shared-derived steps, request cancellation of in-flight local/tool/provider work, suppress returned outputs and prevent subsequent dispatch. If the runtime cannot remove revoked context safely, terminate the affected run and start a fresh permitted-context run only after explicit rebase. A revoke cannot unsend prior provider input.
- At a race between authorization and an already dispatched local/remote action, the check is the ordering boundary, not proof that network time stops. Long-running calls and streamed content require cancellation and a fresh check before each subsequent disclosure/use. No clock/TTL-based stale cache is treated as current access.
- Permission-controlled local cache, embeddings, summaries and artifacts carry lineage. Revoked entries become inaccessible/quarantined immediately on observed invalidation; deletion follows applicable retention policy. Revalidation is mandatory on every reopen/resume and after crashes. Cache files may not be accessible to ordinary agent subprocesses without mediation. If the host cannot enforce that isolation, shared agent processing is gated on that host.
- Connectivity is evaluated per dependency. Loss of the cloud-model connection pauses affected agent work regardless of Task privacy; preserve supported drafts, saved artifacts and run/operation references without promising automatic retry. Loss of Inquello authority blocks shared-derived use even if the model is reachable. A service-only outage does not itself imply model unavailability. A separate private-only Task may continue only if its actual model, runtime and applicable policy/identity requirements remain satisfied; this is not an offline capability. A shared-derived Task cannot be relabelled private or have its lineage removed to continue the same contaminated context. Rebase requires a genuinely fresh permitted-context Task and current authority where required. Shared files or derived results cannot be reopened, extended, exported or used by an agent while current permission is unknown. Local models are not a current priority and are never an automatic fallback.
- A person may still use independently available applications to read/edit their permitted private local files, but this is manual work, not offline AI execution, and this contract does not commit Inquello to a new offline editor. Human-created copies already deliberately exported outside control are disclosed exceptions to recall, not a hidden offline agent mode.
- An output depending on A AND B is accessible only with current rights to both; multiple valid grants to A are OR alternatives. Missing lineage fails closed. To salvage an allowed subset, create a new derivation from permitted inputs with new lineage, not by relabelling the old combined summary.

## 7. Persistence, deletion and recovery — SC-6

- The shared database direction is PostgreSQL; PostgreSQL 18 is the verified implementation seed (current stable documentation verified 2026-10-27); exact patch/driver and deployment compatibility are selected and pinned in the first affected implementation story. Reuse shared Rust domain rules in the service; HTTP framework selection is a replaceable adapter decision, not a second policy implementation. No service or package is installed by this planning run.
- Transactions cover metadata, grant epochs, version registration, durable receipts and outbox records. Immutable blob transfer is outside those transactions: staging/verify/commit/reconcile handles failures. Indexers process committed outbox events idempotently by event ID and source revision; they cannot grant access. Database RLS is defense in depth alongside domain authorization, using non-owner/non-bypass service roles; tenant context is derived from authenticated routing and reset safely between pooled requests.
- Logical schema is introduced per story, not all at project setup: sessions/principals first; membership/policy next; share/version/grant/upload records with sharing; minimum source-version/dependency lineage with artifact registration/sharing and revocation, extended admission/index records only with memory; review coordination when review exists. Migrations are versioned and validated against older supported client contracts.
- Shared blob storage is private and addressed through service-owned opaque keys namespaced by Workspace. Encrypt in transit and at rest; credential/key handling is server-side. Cross-tenant deduplication/existence side channels are excluded. Real provider, region, key management and backup operator remain OQ-16B decisions.
- Deletion first denies new reads/admission and creates a tombstone plus deletion journal entry; consumers remove or quarantine dependent cached/indexed material. Physical deletion, retained evidence obligations, grace windows and backup expiry follow selected data policy, not invented durations. A retained audit event must not preserve deleted source text unnecessarily.
- Restore enters quarantine: revoke old app sessions, reconcile grant/deletion journal from an independently protected current checkpoint with an authenticated high-water mark for all committed authority/deletion events, verify blob manifests and current policies, rebuild or revalidate indexes, then run denial/deletion checks before enabling reads. Freeze writes during restoration/reconciliation or catch up to a verified consistent live high-water mark before reopening; prove journal coverage has no gaps after the restored snapshot, including principal/session revocations. If journal completeness or current restrictions cannot be established, remain unavailable rather than revive historical permissions. Restoring a database is not enough.
- Restore also reconciles the durable command receipt/high-water journal, not only permissions. Rotate `command_epoch` before reopening mutations; old-epoch operation IDs are lookup-only and never replayed as new commands. A previously acknowledged operation missing from restored metadata is uncertain until its durable receipt and resulting effects reconcile; missing journal coverage blocks the affected mutation scope. Clients retain pending operations across reconnect, reconcile them first and must not silently assign a new ID to repeat an uncertain effect. Receipt retention/compaction preserves a rejection tombstone or closed epoch so expiration cannot reopen a duplicate-command path.
- Backup/recovery acceptance is failure injection and restore demonstration for the actual selected route. No RPO/RTO, availability SLA, data-loss tolerance or production region is promised before owner/policy validation. Single-team scope does not waive security and recovery checks.

## 10. Synthetic first-increment topology — SC-7

The first implementation validation environment is an isolated developer/test topology, not a production hosting choice. A trusted local desktop/runtime client talks to a single locally hosted service using the shared Rust domain, PostgreSQL 18 test metadata and a private filesystem-backed implementation of the blob port. All data is generated test material and all principals belong to isolated synthetic Workspaces. No customer source data, production credential, external guest or cross-client policy is introduced.

Identity conformance uses a local OIDC test issuer with deterministic issued-token fixtures and ephemeral test-only signing material, exercising the same SC-1 validation adapter. Test-auth construction is compile/config gated to the test environment; production refuses test issuer/key configuration. Session and policy lifetimes are explicit fixture inputs, not organisational policy or service promises. No credential is generated by this document.

Service transport conformance exercises HTTPS with scoped test-client trust, never a production trust-store change or a bypass of browser security warnings. Browser end-to-end login uses an explicitly trusted development setup when implementation is authorized; approval-dependent host setup is handled at that time. Fixture injection is labelled and never counted as evidence that production SSO/issuer integration works.

The service owns test database/blob migrations and teardown through its normal ports. Temporary test records can demonstrate retention/deletion/recovery behavior with explicit fixture policy, but no fixture duration is a production retention decision. SC-6 restore/journal tests run within this isolated topology; actual production backup/operator/region/data-policy gates remain OQ-16B.

Real cloud-model requests using synthetic inputs remain distinct from mocked protocol fixtures. When separately authorized during implementation, use the inherited default and the selected Claude API-key route with permitted credentials, test budgets and model versions. No simulated model response can satisfy a story that explicitly requires actual inference; obtaining that evidence is acceptance work, not a prerequisite to writing a plan.

This topology resolves the test-stage ownership and configuration decisions without purchasing or provisioning a service now. Actual production configuration must fail closed until OQ-16B requirements are supplied and validated. It does not make real-data permission optional and does not narrow the approved first increment.

## 11. Evidence and limitations

Connectivity clarification from owner message Sentinel_e37ce8af9b048191a6a87aa24934b662: local file storage and tool execution are distinct from model hosting; cloud inference requires connectivity and local models are not a current priority. The owner subsequently adopted the clarified direction; the correction does not create offline AI or approve a supplier.

This is an architecture contract derived from the adopted product/technical direction, not a vendor certification. No executable product code exists in this checkout to ratify the new service; it contains planning/research artifacts. No runtime, security or recovery test ran.

- [RFC 8252](https://www.rfc-editor.org/info/rfc8252/) supports external-browser native-app authorization and PKCE. The specific Inquello session/authority design above is our recommendation.
- [RFC 9700](https://www.rfc-editor.org/info/rfc9700/) requires public-client refresh-token replay defenses, including rotation or sender constraint. Proposed rotation still needs concrete implementation and testing.
- [OpenID Connect Core 1.0, errata set 2](https://openid.net/specs/openid-connect-core-1_0.html) defines authentication claims and validation; identity does not define Inquello resource authorization.
- [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) documents role/owner bypass distinctions; [transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html) documents concurrent behavior and retry requirements. Neither proves application-level access correctness.
