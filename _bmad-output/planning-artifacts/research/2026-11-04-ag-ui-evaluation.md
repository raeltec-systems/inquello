# AG-UI as an agent-to-application protocol for Inquello

Evaluation date: 2026-11-04. Branch inspected: `feat/epic-1-secure-private-desktop`. AG-UI inspected at `github.com/ag-ui-protocol/ag-ui` (main) and `docs.ag-ui.com` (1.0 spec pages). This evaluation is independent of CopilotKit. **Verified** means read in source or docs; **inferred** means my judgement.

## 1. What AG-UI is

**Verified.** AG-UI is an MIT-licensed, event-based protocol for streaming an agent run to a user-facing client. The spec is a JSON Schema (`spec/draft/schema.json`, frozen copy under `spec/1.0/`), with a `proto-freeze.txt` ledger of binary field numbers and a reconciliation report of SDK divergences (`spec/RECONCILIATION.md`). Version 1.0 shipped 2026-09-17 (DEPRECATIONS.md; PyPI `ag-ui-protocol` 1.0.0). Release tags are date-stamped per package (`release/2026-11-03` etc.), not protocol versions.

**Event model (verified from docs/concepts/events and spec/1.0):**
- *Lifecycle:* `RUN_STARTED {threadId, runId, parentRunId?, input?, protocolVersion}`, `RUN_FINISHED {outcome?, result?, usage?, pendingToolCallIds?}`, `RUN_ERROR {message, code?}`, `STEP_STARTED/STEP_FINISHED {stepName}`. `outcome` is `success`, `interrupt {interrupts[]}` or `cancelled`. A stream violation (event before `RUN_STARTED`, nested run, open item at `RUN_FINISHED`) is fatal and the consumer must reject the stream.
- *Text:* `TEXT_MESSAGE_START/CONTENT/END` keyed by `messageId`, with `role`; `TEXT_MESSAGE_CHUNK` as a convenience.
- *Tool calls:* `TOOL_CALL_START {toolCallId, toolCallName, parentMessageId?}`, `TOOL_CALL_ARGS {delta}` (JSON fragments), `TOOL_CALL_END`, `TOOL_CALL_RESULT {messageId, toolCallId, content, role?}`.
- *State:* `STATE_SNAPSHOT {snapshot}` (replace whole state), `STATE_DELTA {delta}` (RFC 6902 JSON Patch, applied in order), `MESSAGES_SNAPSHOT {messages}`.
- *1.0 additions:* `ACTIVITY_SNAPSHOT/DELTA` (UI-only progress messages, never sent back to the agent), `REASONING_*` (replacing `THINKING_*`), `REASONING_ENCRYPTED_VALUE`, `SUBAGENT_STARTED/FINISHED/ERROR`.
- *Escape hatches:* `RAW {event, source?}` and `CUSTOM {name, value}`.
- *Interrupts (human-in-the-loop):* a run ends with `RUN_FINISHED.outcome = {type:"interrupt", interrupts:[{id, reason, message, toolCallId?, responseSchema?, expiresAt?, metadata?}]}`; the client starts a new run with `RunAgentInput.resume = [{interruptId, status, payload, metadata?}]`. The spec says the agent *may* validate `payload` against `responseSchema`; it does not define who may answer. Note a churn signal: the concepts page says `status` is `resolved|cancelled`, the 1.0 pattern page says `answered|abandoned`.
- *Input:* `RunAgentInput {threadId, runId, parentRunId?, protocolVersion?, state, messages, tools, context, forwardedProps?, resume?}`. `tools` are *client-provided* tools the agent may call back; results return as `role:"tool"` messages with `toolCallId` and optional `error`. (Field list assembled from the docs, DEPRECATIONS.md and versioning page; I could not fetch `sdks/typescript/packages/core/src/types.ts` directly.)

**Transports and SDKs (verified).** HTTP POST of `RunAgentInput`, response as SSE (`text/event-stream`) or length-prefixed protobuf (`application/vnd.ag-ui.event+proto`, 4-byte big-endian frames, negotiated by `Accept`). Clients must always accept SSE. First-party SDKs: TypeScript (`@ag-ui/core`, `@ag-ui/client` with `AbstractAgent`/`HttpAgent`, `@ag-ui/encoder`, `@ag-ui/proto`; npm showed version 1.0.3 in the 2026-10-16 release), Python (`ag-ui-protocol`), .NET. Community SDKs: C++, Dart, Go, Java, Kotlin, Ruby, Rust (`sdks/community/rust/crates/ag-ui-client`, client side), Swift. The processing-model page admits Python and .NET parsers "are lenient and have no stripping stage", so only the TS client implements the full enforcement pipeline.

**Governance and maturity (verified).** The `ag-ui-protocol` GitHub org; README says AG-UI "was born from CopilotKit's initial partnership with LangChain and CrewAI"; a biweekly working group and public roadmap. About 17k stars, 5.2k commits, ~300 open issues. 1.0 has a formal deprecation policy (12-month shims expiring 2027-09-17) and a `MAJOR.MINOR` in-band `protocolVersion`. Churn is real: a 2026-10-21 security fix in `ag_ui_adk` 0.11.0 "stops client-supplied state from changing app-wide or user-wide state"; Mastra 2.0 removed the legacy `CUSTOM on_interrupt` event; watsonx changed interrupted streams from `RUN_FINISHED` to `RUN_ERROR`.

**Frameworks emitting it (verified from README):** built-in direct-to-LLM; LangChain/LangGraph, CrewAI (partners); Microsoft Agent Framework, Google ADK, AWS Strands, Mastra, Pydantic AI, Agno, LlamaIndex, AG2 (first party); Claude Agent SDK, Langroid, Cloudflare Agents (community); OpenAI Agents SDK and Bedrock Agents in progress; A2A bridge; Amazon Bedrock AgentCore; MCP Apps for generative UI. There is no Codex app-server adapter.

## 2. Mapping to the Codex app-server protocol and Inquello's extensions

Inquello's wire is JSON-RPC over stdio: client requests (`turn/start`, `turn/steer`, `turn/interrupt`, ~90 `inquello/*` methods, `common.rs:503-1845`), server notifications (`common.rs:2276-2397`) and **server-to-client requests** (`common.rs:2113-2180`). AG-UI has only the second category, plus a one-shot "resume" input.

| Codex / Inquello | AG-UI | Quality |
|---|---|---|
| `turn/started`, `turn/completed` (`common.rs:2308,2310`) | `RUN_STARTED`, `RUN_FINISHED` | Clean; thread→`threadId`, turn→`runId` |
| `item/agentMessage/delta`, `item/started`/`item/completed` for agent messages (`2324,2314,2319`) | `TEXT_MESSAGE_START/CONTENT/END` | Clean |
| `item/reasoning/summaryTextDelta`, `textDelta` (`2354-2356`) | `REASONING_MESSAGE_*` | Clean in shape; Inquello forbids forwarding hidden reasoning (spec 1.26), so it must be dropped |
| Command execution items + `item/commandExecution/outputDelta` (`2335`) | `TOOL_CALL_START/ARGS/END` + `TOOL_CALL_RESULT` | Lossy: AG-UI tool calls assume LLM function-call semantics; sandbox denials, exit codes, "proposed vs applied" (`progress.ts` `application`) become `metadata` or `CUSTOM` |
| `turn/plan/updated` (`2313`) | `ACTIVITY_SNAPSHOT {activityType:"PLAN"}` or `STATE_DELTA` | Lossy: AG-UI plan is model-authored; Inquello's `ProgressStep.status='done'` requires bound completion evidence (`progress.ts:26`) |
| File change items, `turn/diff/updated` | `CUSTOM` / state | No native concept |
| `item/tool/requestUserInput` (server request, `2130`, params `item.rs:1760`) | Interrupt `reason:"input_required"` + `resume` | Approximate: AG-UI ends the run; Codex blocks a request inside the turn with a JSON-RPC `id` and `serverRequest/resolved` (`2340`) |
| `item/commandExecution/requestApproval`, `item/permissions/requestApproval` (`2117,2142`) | Interrupt `reason:"tool_call"` + `resume {approved}` | **Lossy**: see below |
| `inquello/tasks/authority`, `inquello/context/authorize` (server requests, `2173-2180`; `inquello.rs:1349,1644`) | none | No concept: these are runtime-to-host *authority refreshes* answered by main (`main.ts:357`), "never a renderer-controlled verdict" |
| `inquello/permissions/request|pending|decide` with `operationId`, `expectedRevision`, request `revision` 1→2, actor kind supplied by main (`inquello.rs:830-960`) | none | No concept: `resume.payload` is an unversioned JSON blob |
| `InquelloReceipt {operationId, expectedRevision, resultingRevision, replayed}` (`inquello.rs:186`) | none | AG-UI has idempotent resume as a *should*, no receipts |
| Seven state dimensions, each with `actor_kind` and writer rules (`inquello.rs:343-366`; spec 1.15) | `STATE_SNAPSHOT/DELTA` | Lossy and dangerous: AG-UI state is one agent-owned JSON document; Inquello forbids runtime actors writing `review`/`approval_marker` |
| `InquelloToolBoundary`/`InquelloToolReach`, sandbox denials "Blocked: outside this Task's permitted locations" (`inquello.rs:571-600`; spec 1.19) | none | `CUSTOM` only |
| `data_tier` on `inquello/tasks/forThread` (`inquello.rs:1322`), `DataTier::Real` gates (`routes/model.rs:162,245`), route evidence/approval | none | No concept |
| Exact route (`route_id`, `configuration_revision`, credential generation, `InquelloRoutePrivateAuthParams` "never accepted on a socket", `inquello.rs:1070`) | none; `RUN_FINISHED.usage.provider` only | No concept |
| `inquello/tasks/steer|stop|resume` fenced by `expectedRunId/expectedRuntimeId/expectedTurnId` (`inquello.rs:1529`) | new `RunAgentInput` on the thread; `abort()` on the client | Lossy: no fencing against a stale observation |

**Concrete example of the approval gap.** Inquello's `InquelloPermissionRequest` carries `label: "Permission to act"`, an `InquelloCommandEvaluation` naming the exact command, destination, consequences and the controlling rule with its source and revision (`inquello.rs:787-860`); the decision (`inquello.rs:940`) needs `expectedRevision: 1`, an `operationId`, and main supplies `actor_kind` (`human|system|automated_reviewer`). In AG-UI the same thing is `{id:"int-1", reason:"tool_call", toolCallId:"tc-001", message:"Run git push?"}` answered by `{interruptId:"int-1", status:"resolved", payload:{approved:true}}`. There is no operation ID, no revision, no actor, no "deny and forbid this prefix" alternative, and the spec says a producer "need not remember prior interrupts" and "may" validate the payload. Story 1.20's rule that a card is permission, never approval, is purely a convention you would have to carry in `metadata`.

**Inference.** Roughly 60% of what the renderer shows today (messages, running/completed items, plan text, turn boundaries) maps cleanly to AG-UI; everything that makes Inquello *Inquello* (authority rechecks, receipts, state dimensions, tiers, routes, sandbox reach) has to ride in `CUSTOM`, `metadata` or an out-of-band channel.

## 3. What it would and would not solve

**User experience.** AG-UI would give Inquello a well-trodden streaming vocabulary (deltas, reasoning, activity, subagents) and, through the TS client, middleware, subscribers and stream compaction for free. Generative UI is *not* in AG-UI itself: it arrives via the separate A2UI/MCP Apps integrations. Shared state (`STATE_DELTA`) is the headline feature, but Inquello already deliberately rejects a single mutable agent-owned document: `progress.ts` parses a bounded allowlist snapshot, forces `checks='unchecked'` because "prose/references cannot create one" (`progress.ts:34`), and `service.ts:180` says "Notifications are invalidation hints only. No native body reaches the renderer." AG-UI would not improve truthfulness; it would move the burden of enforcing it into an adapter.

**Interoperability.** This is the real prize. An AG-UI endpoint would let a web or mobile client, Slack/Teams bots, or a CLI continue a Task (FR-3, UX-DR45/S12, UX-DR50) using an existing client library rather than Inquello-specific preload operations. It would also let Inquello host third-party AG-UI agents (LangGraph, ADK, Claude Agent SDK). It would **not** solve: identity (no auth model in the spec), tenant isolation (no Workspace concept; `threadId` is the only scope), authority rechecks on resume (spec puts coverage on the consumer, validation optionally on the producer), exact-route disclosure (FR-29), or receipts (AD-7/AD-19).

## 4. Where it could sit

**(a) AG-UI between renderer and main, replacing named preload operations.** *Do not.* Story 1.3 and AD-5 require "no general IPC"; `operations.ts:13-24` and `invokeOperation` (`650-683`) accept one fixed channel per operation with a sender check and a closed-shape validator (`objectPayload` rejects unknown keys, `185-209`). The preload exposes one frozen object and a single push hint, `inquello:tasks-progress-changed` (`preload.ts:111,148`; `main.ts:755`), carrying no body. AG-UI's `RunAgentInput` is an open envelope: `state`, `forwardedProps`, `context`, `tools` and `metadata` are free-form JSON a renderer could fill. That is exactly the "general IPC" the spec forbids, and it would move trust decisions (actor kind, workspace policy, operation IDs, which main supplies today in `operations.ts:510-512`) into renderer-authored payloads. It would also make every `CUSTOM`/`RAW` event a prompt-injection relay from runtime to UI with no allowlist.

**(b) AG-UI adapter in main, projecting Codex events for the renderer.** Acceptable in principle if *one-way and allowlisted*, but it buys little. Main already does a projection (`inquello/tasks/progress` → `parseProgress`), bounded, polled and fenced by principal, Workspace, runtime incarnation and run/turn (spec 1.26). Re-expressing that snapshot as AG-UI events adds a second schema (zod `@ag-ui/core`, a new dependency, which Epic 1 specs forbid without approval) and changes the delivery model from pull-with-invalidation to push, which spec 1.26 excludes ("Do not forward raw native notifications"). No tenant risk if the adapter never accepts `RunAgentInput` from the renderer. Verdict: possible later, not now.

**(c) External AG-UI endpoint for other clients.** The only option with upside, and the riskiest. Security assessment:
- *Renderer sandbox/IPC allowlist:* unaffected if the endpoint lives in main or in `inquello-service`, never in the renderer.
- *Tenant isolation:* AG-UI has no Workspace or principal; the endpoint must be behind the shared service's app session (AD-18), bind `threadId` to a creator-private Task via `inquello/tasks/forThread`, and refuse anything not owned by the caller. The ADK 0.11.0 fix (client state leaking into app/user state) is a live example of this failure class.
- *Authority and receipt integrity:* `resume.payload` must never be applied directly; it must become an `inquello/permissions/decide` with `expectedRevision`, `operationId` and main-supplied actor, and `tasks/steer|stop|resume` must still fence on `expectedRunId/expectedTurnId`. Both are extra adapter logic AG-UI does not express.
- *Prompt injection:* inbound `messages` (system/developer roles exist in the schema), `context`, `state` and `forwardedProps` are all attacker-controlled by design; outbound `CUSTOM`/`RAW`/`metadata` must be stripped or allowlisted. The spec's enforcement stage strips *unknown* material only; it does not sanitise known free-form fields.
- *Data leaving the device:* an HTTP endpoint on the desktop would be a new listening socket, something `InquelloRoutePrivateAuthParams` and the smoke's webRequest allowlist (`security/policy.ts`) currently exclude. Hosting it in `inquello-service` instead means Task content moves to the shared service, which AD-15/AD-21 only allow via explicit, versioned handoff, not implicit upload.

**(d) Inquello consuming third-party AG-UI agents.** Technically clean as a *client* (HttpAgent in main, or the Rust community client in the engine), but every such agent executes tools outside Inquello's sandbox, its tool results are untrusted evidence (FR-34, spec 1.27), and its `STATE_DELTA` cannot be allowed to touch the seven state dimensions. It would be a new processing route needing its own eligibility evidence under spec 1.28, and AD-8's "no silent fallback". Out of V1 scope.

## 5. Trade-offs

- **Maintenance and double translation.** Codex JSON-RPC → Inquello progress snapshot → AG-UI → client UI is three hops; each loses or re-encodes the audit fields in §2. The generated TS types in `desktop/src/protocol/generated` already track the engine; AG-UI adds a second generated contract (`spec/generator`) and the 12-month shim calendar.
- **Spec churn.** 1.0 is seven weeks old; `THINKING_*`, `on_interrupt`, binary input parts and the interrupt `status` vocabulary all changed in 2026. Inquello's "no hand-edited bindings" rule means every AG-UI bump is an engineering task.
- **Testing burden.** Spec 1.28 ties real-data eligibility to a negative-authorization suite for the exact route/build. Any new client surface widens that suite (NFR-3 "negative tests across clients").
- **Lock-in.** Low in principle (MIT, JSON Schema), but the only mature consumer stack is the TS client whose enforcement semantics other SDKs do not yet match; practical lock-in is to CopilotKit's reference client.
- **Benefits.** A standard, tooling-rich stream for secondary clients (S12); framework-neutral vocabulary if Inquello ever hosts or is hosted by other agents; interrupt/resume gives a recognisable shape for "Permission to act" cards in non-desktop clients.

## 6. Recommendation and a safe test plan

**Recommendation: do not adopt AG-UI for the renderer–main or main–engine boundaries in Epic 1 or Epic 2.** It solves none of Inquello's hard problems (authority, receipts, tenant isolation, truthful state) and would weaken two settled decisions (AD-5 named operations, spec 1.26 bounded projection). Keep it on the radar as a **candidate egress format for S12 secondary clients** (option c), to be re-evaluated when CLI/SDK continuation (Story 11.1, FR-23) is designed, and when AG-UI has shipped a second minor without retiring shapes.

**Minimal safe experiment (debug builds only).**
1. Write a pure function in `desktop/src/main/tasks/` (or a Rust module beside `inquello-domain`, which has no engine edit cost) that maps a `ProgressSnapshot` (`progress.ts` types) to an ordered list of AG-UI events: `RUN_STARTED/FINISHED`, `TEXT_MESSAGE_*`, `TOOL_CALL_*`, `ACTIVITY_SNAPSHOT` for the plan, and one namespaced `CUSTOM {name:"inquello:projection", value:{taskId, checks, basis, dataTier, routeId}}`.
2. Feed it only the fictional fixture turns already used by the Story 1.26/1.27 smokes (`inquello_fixture.rs`); no live runtime, no credentials, no PostgreSQL, no real Task.
3. Serialise to SSE text into a file or stdout; consume with a standalone test process using `@ag-ui/client`'s `AbstractAgent` subclass that reads the file. Pin `@ag-ui/core` and `@ag-ui/client` to an exact version in a separate `experiments/` package so no dependency enters `desktop/` (CLAUDE.md: ask before installs).
4. No `RunAgentInput` is ever parsed; no HTTP listener; no `resume`; no state writes. The projection is one-way and read-only, and the mapper must drop reasoning deltas and any item not in the `progress.ts` allowlist.
5. Gate the mapper behind the existing default-off debug fixture build (spec 1.25 "default-off debug fixture build"), never the packaged binary.

**Go/no-go criteria.**
- *Go* to a design spike for option (c) only if all hold: the mapper round-trips every fixture turn with zero spec violations under the TS client's verification (`verifyEvents` rejects nothing); every audit field in §2 survives as `metadata` or the single `CUSTOM` event and is recoverable by the consumer; the AG-UI event stream for a `requestUserInput` turn can be shown to a reviewer who correctly identifies it as "permission, not approval" from the stream alone; AG-UI has published no retired shapes in the two minor releases after 1.0; and the S12 roadmap commits to a non-desktop client.
- *No-go* (stop and record in `deferred-work.md`) if any of: the projection needs a renderer-accepted `RunAgentInput` to be useful; representing Inquello's state dimensions requires `STATE_DELTA` writes from the agent side; the adapter needs a listening socket on the desktop; or the experiment requires edits under `engine/`.
